# EMS MVP Spec

## Product decision

`EMS` should not start as a "live per-extension memory meter for the current tab."

Stable Chrome does not expose reliable live per-extension total memory, and it does not expose a trustworthy "current tab active extension list" primitive.

`EMS` should start as a **site-aware extension control panel** with optional benchmark-backed guidance.

That is the buildable MVP.

## Original request vs feasible MVP

Original request:

1. Trigger by shortcut or click
2. Show extensions active on the current tab and their memory usage
3. Let the user disable one immediately for that tab

Feasible MVP:

1. Trigger by shortcut or click
2. Show extensions that are **likely relevant to the current site**
3. Show their enable state and a lightweight impact label
4. Let the user disable or restore them **globally**
5. Let the user save and restore a per-site extension set

Important wording:

- `likely relevant` is an inference from extension metadata and user-defined sets
- `impact label` is benchmark-derived or heuristic, not live truth
- `disable` is global enable/disable, not true tab-only disable

## User promise

`EMS` helps reduce browser overhead on the current site by surfacing which extensions are likely in play and letting the user switch to a lighter extension set quickly.

It does **not** promise exact live per-extension memory totals.

## MVP scope

### In scope

- Chrome extension popup
- Keyboard shortcut to open popup
- Current site detection
- Installed extension inventory with `chrome.management`
- Current-site relevance inference from:
  - `host_permissions`
  - `optional_host_permissions`
  - `content_scripts.matches`
  - user-defined site profiles
- Global enable/disable for other extensions
- "Save this site setup" and "Restore this site setup"
- Simple impact labeling:
  - `unknown`
  - `low`
  - `medium`
  - `high`
- Import of benchmark results generated by the Windows probe workflow

### Out of scope for MVP

- exact live per-extension memory in MB for the current tab
- true tab-scoped disable
- automatic disable without explicit user action
- cross-browser support
- background daemon or always-on monitoring

## Core UX

### Popup: current site

Header:

- current tab title
- current origin
- quick actions:
  - `Lighten this site`
  - `Restore previous state`
  - `Save current setup`

Extension list rows:

- extension name
- enabled/disabled pill
- relevance reason:
  - `matches this site`
  - `optional access`
  - `saved for this site`
  - `unknown`
- impact label:
  - `unknown`
  - `low`
  - `medium`
  - `high`
- action button:
  - `Disable`
  - `Enable`

### Lighten this site

Behavior:

- use the saved allowlist for the current origin if it exists
- otherwise keep only:
  - extensions explicitly pinned by the user
  - extensions marked `allow on all sites`
- disable the rest globally
- save the pre-action state for one-click restore

### Restore previous state

Behavior:

- restore the exact set of extensions that were enabled before the last EMS action

### Save current setup

Behavior:

- store the current enabled-extension set as the preferred set for the current origin

## How site relevance is inferred

`EMS` cannot ask Chrome "which extensions are active on this tab right now."

Instead it should compute a ranked relevance set:

1. Explicit site profile match
2. `content_scripts.matches` contains the current URL
3. `host_permissions` contains the current URL
4. `optional_host_permissions` contains the current URL
5. Unknown

This must be described in the UI as `likely active on this site` or `site-relevant`, not as a hard claim.

## How impact is shown

### Default mode

Without imported measurements, show:

- `unknown`

### Benchmark-backed mode

The Windows probe produces scenario-level results outside the extension.

Those results can be distilled into a small local catalog:

```json
{
  "extensions": {
    "eimadpbcbfnmbkopoojfekhnkhdbieeh": {
      "label": "medium",
      "notes": "YouTube scenario: renderer delta observed"
    }
  }
}
```

The extension imports this catalog and shows:

- impact label
- short scenario note

This is feasible because the extension is displaying prior measured guidance, not claiming live direct measurement.

## Architecture

### Component A: EMS Chrome extension

Responsibilities:

- popup UI
- current tab URL read
- installed extension inventory
- enable/disable actions
- local storage for:
  - site profiles
  - restore snapshot
  - pinned extensions
  - imported benchmark labels

Relevant APIs:

- `chrome.management`
- `chrome.tabs`
- `chrome.storage`
- `chrome.commands`

### Component B: EMS probe workflow

Responsibilities:

- run focused benchmark scenarios
- produce JSON snapshots and diffs
- optionally export simplified impact labels for import into the extension

This already exists in this repository as the Windows measurement harness.

### Component C: optional importer

Responsibilities:

- map benchmark findings to stable labels
- export/import a compact JSON file

This can be implemented after the popup MVP.

```json
  "allowedExtensionIds": [
```


## MVP success criteria

`EMS MVP` is successful if:

1. the user can open the popup on any page
2. the popup lists installed extensions with site-relevance reasoning
3. the user can disable and restore selected extensions reliably
4. the user can save a site-specific extension set
5. the UI clearly avoids claiming exact live memory truth

## Implementation order

### Step 1

Build the extension shell:

- manifest
- popup
- `chrome.management` inventory
- current tab origin display

### Step 2

Add enable/disable and restore:

- disable selected extension
- snapshot previous enabled state
- restore button

### Step 3

Add site profiles:

- save current setup for this origin
- restore preferred setup for this origin
- pin extension support

### Step 4

Add relevance inference:

- parse host permissions
- parse content-script matches
- show ranked relevance reasons

### Step 5

Add imported impact labels:

- JSON import
- label rendering
- notes rendering

## Risks

1. `chrome.management` permissions may feel sensitive to users
2. Chrome Web Store review may scrutinize mass enable/disable behavior
3. Host-permission inference can produce false positives
4. Benchmark labels can be over-trusted if the UI wording is sloppy

## Non-negotiable wording rules

Do not say:

- `active extensions on this tab`
- `live memory usage`
- `this extension uses 120 MB right now`

Prefer:

- `likely relevant on this site`
- `benchmark-based impact`
- `previous measured scenario`

## Recommended next move

Start implementing the Chrome extension popup MVP now.

Do not wait for perfect measurement.

The current evidence is already strong enough to build a useful control panel product.
